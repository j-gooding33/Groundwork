# Running Groundwork on a Mac

The game code is written: the simulation (`GroundworkCore`), everything the app decides (`GroundworkView`), and the iPhone app itself (`App/Groundwork`, SwiftUI and SpriteKit). The first two are tested on Linux. The app layer has only been checked with stand-ins for Apple's frameworks, so **expect a short round of compile fixes the first time you build it in Xcode**. Paste any errors to Claude Code and it will fix them.

Screenshots of what the app should look like, rendered from the real code: `docs/screenshots/`.

## 1. Open it on your Mac

The Xcode project is already in the repo (`Groundwork.xcodeproj`), so there is nothing to create by hand.

1. Install Xcode from the App Store, open it once, and let it install the iOS simulator.
2. Get the repo. In Terminal:
   ```
   git clone https://github.com/j-gooding33/Groundwork.git
   cd Groundwork
   ```
   It's private: if git asks you to sign in, use GitHub Desktop or `gh auth login`.
3. Run `bash Tools/setup_mac.sh`. It runs the game-logic tests on macOS, builds the app for the simulator, saves any compile errors to `build/errors.txt`, and opens Xcode.
4. In Xcode, pick an iPhone simulator at the top and press **Run** (Cmd+R).

If the build fails, either paste `build/errors.txt` to Claude Code, or connect this folder so Claude can build and fix it directly: in the Claude desktop app go to **Settings → Claude Code → Remote Control** and add the `Groundwork` folder, or run `claude remote-control` inside it.

To play on your own iPhone, sign in under **Xcode → Settings → Accounts** with a free Apple ID, choose your team under the target's **Signing & Capabilities**, plug in the phone and press Run.

### What the project contains
- **App sources:** `App/Groundwork` is a synced folder, so any Swift file added there joins the app automatically.
- **Package:** the local package `GroundworkCore/` provides the `GroundworkCore` and `GroundworkView` libraries.
- **App icon:** `App/Groundwork/Assets.xcassets/AppIcon.appiconset`, made from the game's sprites by `Tools/make_icon.py`.
- **Resources:** `Data/` and `Art/generated/` are bundled as folder references. The code loads `Data/...` and `generated/atlas.png`.
- **Settings:** iOS 17, iPhone and iPad, landscape only, full screen, status bar hidden, bundle id `com.groundwork.Groundwork` (change it if you like).
- **Generated by `Tools/make_xcodeproj.py`.** Small changes can be made in Xcode. If you re-run the generator, it overwrites the project. `python3 Tools/check_xcodeproj.py` checks the file without Xcode.

## 2. How it fits together

| Layer | Where | What it does | Tested |
| --- | --- | --- | --- |
| Simulation | `GroundworkCore` | World, ticks, production, belts, Trace, chapters, saving | Linux |
| Presentation | `GroundworkView` | Which sprites to draw and where, terrain edges, belt pieces, item gliding, villagers, day and night, camera, touch gestures, tools, effects, HUD contents, autosave timing | Linux, plus the screenshots |
| App | `App/Groundwork` | Puts those sprites on screen with SpriteKit, the HUD with SwiftUI, plays haptics and sound | Stand-in type-check only, until Xcode |

The rule that keeps this working: **the app only reads `GameSession` and sends it commands, and makes no decisions of its own.** If something needs deciding (what a tap does, what to draw), it goes in `GroundworkView` with a test.

### App files

- `GroundworkApp.swift`: entry point; saves whenever the app leaves the foreground.
- `GameStore.swift`: owns the `GameSession`, the camera and input state. Runs the frame loop: ticks, effects, HUD refresh, autosave every 30 seconds. Turns touches into gestures and commands, and saves to Application Support.
- `TitleView.swift`: ten builders lay bricks spelling GROUNDWORK (1.8 s, tap to skip; timing in `GroundworkView/IntroAnimation.swift`), then Tutorial (or Continue tutorial), New world, Restart tutorial, Settings, and your saved worlds (tap to play, hold to delete). New world asks for a name, a seed (with a dice button) and how much water, forest and clay, and shows the map before it is made. Saves live in Application Support/Groundwork: `tutorial.json` and `worlds/<id>.json`.
- `GameView.swift`: the world fills the screen, with controls at the edges:
  - build palette on the left;
  - chapter name, goal bar and clock on top;
  - selected building on the right (status, rates, "runs out in", Pick up, Trace);
  - mode tabs at the bottom (Build, Trace, Undo to start; Demolish and speed after the tutorial);
  - tutorial bubble, what the picked tool does, toasts, the chapter-complete card (Continue opens the next chapter) and the pause menu.
- `WorldScene.swift`: an `SKScene` at 480×270, scaled up with nearest-neighbour filtering. It matches one node per sprite id to `SceneBuilder`'s output each frame, moves the camera, applies the day/night tint, and plays bounces, squashes, dust, floating "+1"s and the goal light sweep.
- `Atlas.swift`: textures from `atlas.png`, nearest filtering.
- `Feel.swift`: haptics, plus placeholder sound generated in code: a machine hum that follows throughput, every sound cue, and a soft music pad that gains layers with each milestone.
- `Theme.swift`: colours from the palette and atlas icons for SwiftUI.

### How a game goes

Everyone starts with the tutorial: one handcrafted world, played in chapters. Buildings carry over from one chapter to the next, and each chapter draws more of the map (you can't build on blank paper yet).

1. **Bare Ground:** dig clay, bake bricks, fill the foundation. Teaches carrying, belts and Trace.
2. **First Belts:** a crate appears; fill it with 20 bricks by belt. Teaches a second pit and merging belts.
3. **Stone to Roof:** sawmill and builder's yard; five cottages build themselves once supply is steady.
4. Five cottages finish the tutorial. The card offers **Make a new world** or **Keep building here** (Free Build: the whole map, everything unlocked, no goal).

New worlds are generated from their seed. Everything is unlocked, there is no goal, and for the first hour a tip appears when something becomes useful (tap it away; it also goes once you do the thing).

Landmarks are named on the map ("Clay", "Forest", "Lake") until you use them, and the first building of each type shows its name and what it does for ten seconds.

### Controls

- **Tap a building with no tool:** pick up what it has made, or drop what you're carrying. Its panel opens either way.
- **Build palette:** tap a building (a line at the bottom says what it does), then tap the map; 2×2 buildings centre under your finger. Tap the selected button again to put the tool down.
- **Belt:** choose it in the palette, then drag from a building to where the belt should go, or tap one building and then the other. A ghost shows the route before you let go. Letting go on or right next to a building connects to it (buildings are drawn a tile taller than the ground they stand on). While the belt tool is out, every building shows what it takes and makes ("clay log ▸ brick").
- **Connections:** small arrows show where items leave a building and go into one, a junction shows where one belt joins another, and a red cross marks a belt that runs into nothing.
- **Trace tab:** tap a building to see its chain. Gold dots flow along working links, a red marker bobs over the step to fix, and the right-hand panel lists every step with its state and reason. Tap a row to jump the camera there.
- **Status bubbles** appear over stuck machines without opening anything: the missing item's icon, an up-arrow for a full output, a slashed circle for a used-up source, an hourglass for running slow.
- **Rates tab** (after the tutorial): labels under each working building with made and used per minute, and a warning when an input will run out within a minute.
- **Tutorial:** tap the bubble to tuck it away and "?" to bring it back. A gentle hint appears if a machine has been stuck for 30 seconds. **Skip tutorial** is in the pause menu.
- **Long press:** open a building's panel. **One finger:** pan (lays belts while the belt tool is out). **Two fingers:** always pan and zoom.

## 3. Day-to-day commands

| Task | Command |
| --- | --- |
| Simulation and view tests | `cd GroundworkCore && swift test` |
| Rebuild the sprite atlas after editing art | `python3 Tools/make_art.py` |
| Rebuild the app icon from the sprites | `python3 Tools/make_icon.py` |
| Render screenshots of the real game | `bash Tools/preview.sh`, writes `docs/screenshots/` |
| Check app code without a Mac | `bash Tools/check_app.sh` |
| Performance check | `cd GroundworkCore && swift run -c release GroundworkBench` |

Edit sprites as text grids in `Art/sprites/`, or hand-paint PNGs into `Art/manual/` (they always win). Rebuild the atlas afterwards; the app picks up `Art/generated/` on the next build.

## 4. Known gaps

- **Not yet built against Apple's SDK.** The stand-ins match the real API as closely as I know it, but expect a few compile fixes.
- **Performance on a device is unmeasured.** The static layer (terrain, edges, trees) is about 5,000 sprite nodes drawn from one texture. If it's slow on an older iPhone, render that layer to a single texture once with `SKView.texture(from:)`.
- **Sound is generated placeholder tones.** Replace the buffers in `Feel.swift` with real audio when it exists.
- **Text uses the system monospaced font,** not a pixel font.
- **The balance numbers in `Data/` are placeholders.** Play it and tune.
